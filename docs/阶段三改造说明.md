## 一、机制一：工具按需注入（会话调度省 token）

### 问题
每轮请求把 20+ 个工具的全量 schema 注入；纯闲聊轮这些全是白花的 token，且小模型面对 20+ 工具容易乱选（该发言时去翻记忆）。

### 三层门控（`src/tool-gate.js`，纯函数可独立测试）

| 层 | 成本 | 行为 |
|---|---|---|
| 规则层（默认，`toolGate='rules'`） | 零成本零延迟 | ①@机器人→全量（被请求强信号）②消息带图→至少开 media ③纯闲聊形态（哈哈/嗯/睡了睡了/666…）→ 只留常驻工具 ④信号词（天气/图里/上次/翻译…）→ 只开对应类别 ⑤长文本(>40字)→全量 ⑥短而含糊→全量保底 |
| Jev 层（`toolGate='jev'`） | ≤1 次本地 0.8B 推理（仅规则判不准时） | 问 `toolNeedGate` 角色「这轮要不要查资料/看图/翻记录」，TOOL→全量，CHAT→只留常驻；弃权/失败/本地没起→全量保底 |
| 保底 | — | 任何判不准的情况都回到全量。**宁可多花 token，不可漏工具** |

### 砍什么、留什么
- **砍**：三类信息工具的 schema —— search（web_search/web_fetch/search_images/search_bilibili…）、media（get_message_images/identify_image…）、memory（memory_query/memory_search…）
- **永远留**：发言类（send_message/send_sticker/send_image…）与群聊辅助（get_recent_messages…）——模型开口必须用 send_message，门控只裁「信息获取」面不裁「表达」面
- 未收录的新工具默认常驻（新技能不因门控漏注入）

### 工具结果硬上限（防单轮 token 爆炸）
- **单工具截断**：默认 6000 字符（`api.toolResultMaxChars`），超长截断+尾注提示原文长度（web_fetch 整页 HTML 是单轮爆炸主因）
- **轮内累计预算**：默认 12000 字符（`api.toolResultBudgetChars`），用尽后后续结果替换为「预算用尽」提示，逼模型收口而不是无限索取

### 缓存权衡（明示）
门控档位按消息变化 → 同会话不同轮的 tools 前缀可能不同 → 端点 prompt cache 的 tools 块偶发重建。闲聊轮省下的 schema token 通常远大于偶发重建代价；要极致缓存稳定可 `toolGate='off'`。

### 会话可观测
每轮的判定结果记在 `session.toolGate`（mode/need/cats/reason/toolsBefore/toolsAfter），控制台可查；console 打印裁剪明细。

## 二、机制二：模型通道（本地/云端二选一 + 回退）

### 配置（`data/config.json` → api 段）
```jsonc
{
  "api": {
    "baseUrl": "https://api.deepseek.com/v1",     // 云端端点（现有字段不变）
    "apiKey": "sk-…",
    "model": "deepseek-chat",

    "channel": "cloud",                            // 'cloud'（默认=0.5 行为）| 'local' | 'auto'
    "local": {                                     // 本地 OpenAI 兼容端点
      "baseUrl": "http://127.0.0.1:18080/v1",     // 默认=localJev 的 llama-server
      "model": "",                                 // 留空 → 自动 GET /models 探测（30s 缓存）
      "apiKey": ""                                 // llama-server 默认免鉴权
    },
    "fallback": "local-to-cloud"                   // channel=local 时：'local-to-cloud'（默认）| 'none'
  }
}
```

### 语义
| channel | 主通道 | 失败回退（一次性，不反复横跳） |
|---|---|---|
| `cloud`（默认） | 云端 | **无**（行为与 0.5 完全一致，兼容优先） |
| `local` | 本地端点 | `fallback='local-to-cloud'` 且云端已配 → 换云端重试；`'none'` → 纯离线不回退（避免误花钱） |
| `auto` | 云端配全→云端；**云端没配 Key→本地**（离线开箱即用） | 云端失败→换本地试一次 |

### 覆盖面
- **主对话**（chatCompletionWithRetry）：通道以 overrides 注入（复用现有机制，对记忆整理等调用方零影响）；回退发生在重试循环里（换通道不消耗重试预算）
- **Jev 决策**：本来就有三通道（local / localJev.cloud / auto 弃权升级），0.6 保持原语义；**没本地模型的用户**可把 `localJev.cloud.enabled=true` 让 Jev 全走云端
- **其他用模型处**（vision 识别等）：跟随主 `api` 通道；但视觉需多模态能力，本地 0.8B 一般不支持——`api.local` 指向多模态本地服务（Ollama/LM Studio）时才有效，文档明示
- 本地端点探活/模型名探测：`probeLocalEndpoint()`（GET /models，1.5s 超时，30s 缓存）

### 典型玩法
1. **全离线**：勾本地 Jev（llama-server 起来）+ `channel:'local'` + `fallback:'none'` → 一分钱不花
2. **离线优先省钱**：`channel:'local'` + `fallback:'local-to-cloud'` → 本地挂了自动走云端
3. **云端优先+离线兜底**：`channel:'auto'` → 云端网络抖动时本地救场
4. **纯 0.5 行为**：什么都不改（默认即兼容）
